# Site Harness Installation — Chouinard Studios Implementation Evidence

**What happened in this specific Customer Zero installation.** Generalisable
guidance derived from it lives in
[SITE-HARNESS-INSTALL-GUIDANCE.md](SITE-HARNESS-INSTALL-GUIDANCE.md) — do not
treat the file paths here as universal instructions.

The site token is deliberately not reproduced in this document. It exists only
at the single integration location where it is required.

## What was installed

The AI Support snippet exactly as generated by the normal public onboarding
flow: one `<script>` element loading `track.js` from the AI Support production
host, carrying `businessId` and `siteToken` query parameters. Unmodified — same
src, same host, same parameters, no attributes added.

## Framework detection

| | |
|---|---|
| Framework | Next.js 16.3.0, App Router |
| UI runtime | React 19.2.8 |
| Rendering | Fully static — all 32 routes prerendered at build time |
| Host | Vercel |

**How it was identified:** `package.json` dependencies plus the presence of an
`app/` directory with a root `layout.tsx`. From outside, the served HTML is the
faster tell — `/_next/static/...` asset paths and a `self.__next_f.push(...)`
hydration payload both appear in the page source.

## Where the snippet belongs here

**One file changed: `app/layout.tsx`.**

That is the single root layout. This site has **zero nested layouts**, so one
insertion covers every public route. The tag sits immediately before the
closing `</body>`, after all existing content.

## Whether raw `<script>` worked

Yes — but the choice was not free, and the obvious choice is wrong.

### Finding 1 — the naive paste fails the framework's own lint

Pasting the snippet as-is produces a hard lint **error**, not a warning:

```
99:9  error  Synchronous scripts should not be used.
             See: https://nextjs.org/docs/messages/no-sync-scripts
             @next/next/no-sync-scripts
```

Verified empirically: removing the suppression comment reproduces it; restoring
it clears it. A customer whose CI runs lint would see the build fail.

### Finding 2 — the framework's recommended fix breaks detection

The Next.js guidance that error links to steers the developer to `next/script`.
Its default `afterInteractive` strategy injects the tag **client-side after
hydration**, which means the tag is **absent from the served HTML**.

For a static site whose pages are prerendered, that turns a tag any fetcher
could see into one only a JavaScript-executing client can see. If AI Support's
connection check or crawler reads HTML without executing scripts, the
correct-looking framework fix silently breaks it.

**Resolution used here:** keep the plain `<script>` tag so the emitted HTML
matches what a plain HTML page would serve, and suppress the lint rule on that
one line with a comment explaining why.

## CSP, hydration, SSR, routing, deployment

| Concern | Outcome |
|---|---|
| CSP | None configured. No conflict. `next.config.ts` sets only `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`. |
| Hydration | No mismatch. React 19 matched the SSR'd tag; it is not re-inserted or re-executed on hydration. |
| SSR / SSG | All routes static. The tag is emitted into every prerendered HTML file. |
| Client-side routing | The root layout does not remount on soft navigation, so the tag persists and is **not** re-requested. Verified. |
| Deployment | Normal path — push to `main`, Vercel builds and deploys. No special mechanism. |
| Existing analytics | `lib/analytics.ts` is a no-op vendor-neutral abstraction with **zero network calls**. Not a tracker, not a duplicate. |
| Existing chatbot | None. No second harness was added. |

## How "exactly once" was verified

Three layers, because the first two can mislead:

1. **Source** — one occurrence in the repository, in one file.
2. **Prerendered HTML** — a naive `grep` reports **two** matches per page. Only
   one is an executable `<script>` tag; the second is inside the escaped RSC
   hydration payload (`\"$\",\"script\",null,{\"src\":...`) within
   `self.__next_f.push(...)`. Counting text matches would have produced a false
   duplicate alarm.
3. **Real browser** — one `script[src*="track.js"]` element and exactly one
   network request per route, across five local routes and six production
   routes. No second request after client-side navigation.

## Production verification

Against `https://chouinardstudio.com`, in a real browser, without calling any
AI Support API or seeding any record:

- `/`, `/music`, `/stories`, `/studio`, `/contact`, `/current-work` — one tag,
  one request each; first load `200`, subsequent `304`
- The script **executes**: `window.hasTracked` is set
- Homepage renders normally; no uncaught page errors
- Exactly one harness element in the DOM

## Steps requiring engineering knowledge a business owner would not have

Recorded because each is a candidate for removal by the product, not by this
customer:

1. Knowing that `app/layout.tsx` is the site-wide insertion point — and that
   nested layouts, had any existed, would risk multiple insertions.
2. Recognising that the lint error is safe to suppress here rather than
   "fixing" it the way the framework suggests.
3. Understanding that `next/script`'s default strategy would remove the tag
   from the served HTML.
4. Distinguishing the RSC hydration payload from a genuine duplicate.
5. Knowing that soft navigation does not remount the root layout, so no
   duplicate request occurs.

A non-developer would plausibly get 1 right and 2–5 wrong.

## Ambiguities in the AI Support instructions as received

- The snippet arrived with no framework-specific guidance and no statement of
  **where** it must appear — head or body, initial HTML or post-hydration.
- No statement that the tag must be present in the **served HTML** rather than
  merely in the DOM. That constraint had to be inferred, and it is precisely
  the constraint the framework's own advice violates.
- No verification instructions a non-developer could follow.
- The onboarding UI states this one script also powers the assistant, so no
  second harness was added. That was clear and correct.

## Outstanding condition unrelated to this installation

`chouinardstudio.com` still serves `robots.txt` with `Disallow: /` and
page-level `noindex`, because launch indexing has not been enabled.

The harness is a browser-executed beacon and is unaffected — it loads and runs,
as verified above. **Crawl-based ingestion remains blocked.** This is the
precondition already recorded in
[FIRST-TRIAL-PROTOCOL.md](FIRST-TRIAL-PROTOCOL.md) and
[AI-SUPPORT-HANDOFF.md](AI-SUPPORT-HANDOFF.md), and it was deliberately **not**
worked around here.
